# Releasing DigiAsset for Windows

Releases are built **locally on Windows and uploaded by hand**. There is no release
workflow, and that is deliberate — see [Why there is no CI release](#why-there-is-no-ci-release).

## Steps

1. **Bump the build number.** `WIN_BUILD` in `CMakeLists.txt` is the source of truth; it is
   substituted into `src/Version.h.in` -> the generated (gitignored) `src/Version.h`. Never
   hand-edit the generated header.

   ```
   SET(WIN_BUILD 137)
   ```

2. **Build Release and run the tests.**

   ```
   cmake -B build -S .
   cmake --build build --config Release
   cd build && .\tests\Release\Unit_Tests_run.exe
   ```

   All unit tests must pass. `Google_Tests_run` is a separate suite that needs a live
   DigiByte Core and IPFS; it is not part of the release gate.

3. **Stage the assets.**

   ```
   powershell -ExecutionPolicy Bypass -File .\tools\stage-release.ps1
   ```

   This collects the six published assets, **regenerates `web.zip` from `web\`**, writes
   `SHA256SUMS` over all of them, and reads the version back out of the built binary so a
   stale build cannot be staged against a bumped `WIN_BUILD`.

4. **Create the release** with the command the script prints, from `release-staging`.

5. **Verify from the published release**, not from the staging folder:

   ```
   curl -sL -O https://github.com/chopperbriano/DigiAssetWindows/releases/latest/download/SHA256SUMS
   # download each asset, then:
   sha256sum -c SHA256SUMS
   ```

## Published assets

All seven must be present or the documented `/releases/latest/download/<file>` URLs 404:

| Asset | Source |
|---|---|
| `DigiAssetWindows.exe` | `build/src/Release/` |
| `DigiAssetWindows-cli.exe` | `build/cli/Release/` |
| `DigiAssetPoolServer.exe` | `build/pool/Release/` |
| `example.cfg` | repo root |
| `seed-digibyte.ps1` | `snapshots/` |
| `web.zip` | regenerated from `web/` |
| `SHA256SUMS` | generated by `stage-release.ps1` |

`web.zip` is **not** produced by CMake. A stale `build/web.zip` was nearly shipped once;
`stage-release.ps1` rebuilds it from source every time for that reason.

## Checksums

`SHA256SUMS` is published with every release and verified on download by both
`setup-digiasset.ps1` and `node/update-binaries.ps1`. A **mismatch is fatal** and leaves the
working binary untouched; a **missing** file only warns, so rolling back to a release from
before win.133 still installs.

It is written with **LF** line endings. `Set-Content` emits CRLF on Windows, and coreutils
`sha256sum` then reads the trailing `\r` as part of the filename — every line fails while the
hashes themselves are correct.

**Honest scope:** the sums ship in the same release as the binaries, so this catches a corrupt
download or a wrong file attached to a release. It is *not* protection against a hostile
release — that needs Authenticode signing, which this project does not currently do.

## Why there is no CI release

`.github/workflows/release.yml` was removed in win.137. It built Linux, macOS and Windows
artifacts on every `v*` tag and **had never once succeeded in 20 runs**, so every release
this project cut left a red X on the repository. It also could not produce what is actually
shipped: the release assets are MSVC Release binaries built against vendored dependencies and
a NuGet Boost, and the workflow's Linux and macOS jobs have no meaning for a Windows fork.

`windows-build.yml` remains as the CI guardrail — it builds node + CLI + pool on MSVC and
runs the unit suite on every push and PR. It mirrors the documented local build, including
applying `patches/libjson-rpc-cpp-cmp0042.patch`, so CI and a developer machine stay in step.
